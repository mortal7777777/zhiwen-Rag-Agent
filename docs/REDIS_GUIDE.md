## 第一部分:体系建立

## 1. Redis 是什么,为什么快

**Redis = 开源的内存键值数据库**:所有数据存内存,支持丰富数据结构,单线程
事件模型处理命令,常被用作缓存/分布式锁/计数器/消息队列。

**为什么快(面试必背 4 点)**:
1. **纯内存**:读写无磁盘 IO(磁盘只参与持久化,异步);
2. **单线程 + IO 多路复用**:epoll 监听多路 socket,一个事件循环顺序处理命令
   ——无锁、无上下文切换开销、无并发竞争问题;
3. **高效数据结构**:跳表/哈希表/压缩列表,均为精心优化的实现;
4. **RESP 协议简单**:文本协议解析快。

> 单线程的"代价":一个慢命令(如 KEYS *)会阻塞所有客户端 → 生产禁止 KEYS,
> 用 SCAN。6.0 引入 IO 线程池(只负责读写 socket,命令执行仍单线程)。

## 2. 五种基础数据结构与底层实现

### 2.1 String(字符串)
- 底层:`SDS`(简单动态字符串,Redis 自研):O(1) 取长度、二进制安全、
  预分配空间(拼接不频繁 realloc)、惰性空间释放;
- 使用场景:缓存对象(JSON 序列化)、计数器(INCR:点赞/限流/库存)、
  分布式锁(SETNX)、session;
- 内部编码:embstr(短串,连续内存) / raw(长串) / int。

### 2.2 Hash(哈希)
- 底层:数据少时 `listpack`(紧凑连续内存),量大转 **哈希表**(渐进式 rehash);
- 场景:对象字段存取(用户信息 hset user:1 name xx age 18)、购物车;
- 为什么比 String 存对象好:改单个字段不用整体反序列化,省内存省带宽。

### 2.3 List(列表)
- 底层:listpack → 双向链表 `quicklist`(多段压缩列表);
- 场景:消息队列(LPUSH+BRPOP 阻塞消费)、最新列表(LRANGE)、
  关注/粉丝时间线;
- 注意:作为队列没有 ack/重投机制 → 可靠队列用 Stream(见 §2.6)。

### 2.4 Set(集合)
- 底层:整数数组(intset,小数据) / 哈希表;
- 场景:去重(SADD)、点赞/收藏、标签、**交并差运算**(共同好友:
  SINTER 用户 A 与用户 B 的关注集合)。

### 2.5 ZSet(有序集合,Redis 招牌)
- 底层:`skiplist + dict`(跳表按 score 排序,字典按 member 定位);
  为什么用跳表不用红黑树:实现简单、范围查询友好(双向遍历),且 Redis 的
  跳表是改良版(层高随机、双向指针);
- 场景:**排行榜**(ZADD score,ZREVRANGE TopN)、延迟队列(score=执行时间戳,
  ZRANGEBYSCORE 取到期任务)、限流滑窗、带权调度;
- 面试手撕:跳表查找/插入平均 O(logN),最坏 O(N)。

### 2.6 进阶结构(加分项)
| 结构 | 底层 | 场景 |
|---|---|---|
| Bitmap | String 位操作 | 签到/日活统计(SETBIT/GETBIT/BITCOUNT) |
| HyperLogLog | 概率结构(12KB) | UV 去重统计(误差 ~0.81%) |
| GEO | ZSet + 编码 | 附近的人(GEORADIUS) |
| Stream | 持久化消息流 | 可靠消息队列(XADD/XREADGROUP,消费者组/ACK) |

## 3. 持久化:RDB 与 AOF

| | RDB(快照) | AOF(追加日志) |
|---|---|---|
| 原理 | fork 子进程把全量数据写 .rdb 文件 | 每条写命令追加 .aof 文件 |
| 恢复 | 快(二进制) | 慢(重放命令) |
| 丢失 | 可能丢最后一次快照后的数据 | 按 appendfsync 策略(always/everysec/no) |
| 体积 | 紧凑 | 大(可 AOF 重写压缩) |
| 阻塞 | fork 时有阻塞;bgsave 不阻塞主线程 | 追加不阻塞 |

**写时复制(COW)**:RDB 的 fork 子进程与主进程共享内存页,子进程写新页,
主进程写时复制 → fork 瞬间不拷贝全量内存,只复制页表;
**混合持久化(4.0)**:RDB 全量 + AOF 增量,兼顾恢复速度与丢失窗口;
面试答法:默认两者都开(AOF everysec),可容忍秒级丢失。

## 4. 过期与内存淘汰

- **过期**:惰性删除(访问时检查)+ 定期删除(抽样清理);为什么不用定时删除:
  需要维护定时器,大量 key 时开销大;
- **8 种淘汰策略**(maxmemory-policy),面试记住 4 个:
  - `noeviction`:不淘汰,写报错(默认);
  - `allkeys-lru`:全键 LRU;
  - `volatile-lru`:只对设置过期的键 LRU;
  - `allkeys-lfu` / `volatile-lfu`:LFU(按访问频率,防"冷门大对象"长期霸占);
- 近似 LRU:真正的 LRU 需要双向链表 O(1) 维护,Redis 用抽样(默认抽 5 个)
  近似实现,省内存。

## 5. 缓存三大问题(必考)

| 问题 | 现象 | 解决方案 |
|---|---|---|
| **穿透** | 查不存在的数据,请求打到 DB | ① 空值也缓存(短 TTL)② 布隆过滤器前置 ③ 参数校验 |
| **击穿** | 热点 key 过期瞬间,大量请求打到 DB | ① 互斥锁重建(只让一个线程回源)② 逻辑过期(不真正删,后台续)③ 热点永不过期 |
| **雪崩** | 大量 key 同一时间过期/Redis 宕机 | ① TTL 加随机抖动 ② 多级缓存(本地缓存 Caffeine + Redis)③ 熔断降级 ④ 集群高可用 |

**缓存一致性(双写)**:写 DB 后删缓存(删而非更新,避免并发写覆盖脏值);
删除失败用**延迟双删**或订阅 binlog 异步删;最终一致性是常态,强一致
(读后写)才需要"先删缓存再写 DB + 短锁"。

## 6. 分布式锁(高频)

**实现(Redis 单点版)**:
```lua
-- 加锁:SET key value NX EX seconds(原子,带过期防死锁)
SET lock:order  <client_id> NX EX 30
-- 解锁:先校验持有者再删(防误删别人的锁)
if redis.call("get", key) == ARGV[1] then return redis.call("del", key) else return 0 end
```
- **为什么必须 Lua/原子**:GET+DEL 两步有窗口,可能删掉别人的锁;
- **value 用唯一 client_id**:防止"自己超时后锁被别人拿到,自己又去解锁";
- **看门狗(Redisson)**:锁快到期时任务没跑完 → 自动续期,防止锁提前释放;
- **主从切换的坑**:主节点挂了,锁还没同步到从节点 → 锁丢失;红锁(Redlock)
  多节点过半加锁缓解,但有争议(时钟漂移/性能),中小厂一般不用;
- 面试答法:SET NX EX + Lua 解锁 + client_id + 看门狗续期;
  高可用场景谈 Redlock 与 ZK/etcd 方案对比。

## 7. 高可用:主从 / 哨兵 / 集群

### 7.1 主从复制
- 全量同步(RDB 快照 + 增量缓冲)+ 增量同步(offset 断点续传);
- 6.0 之前主从复制也是"异步"的 → 主从延迟;
- 用途:读写分离、容灾。

### 7.2 哨兵(Sentinel)
- 独立进程组监控主从;**主观下线**(本哨兵联系不上)→ **客观下线**
  (多数哨兵同意)→ 选新主(淘汰规则:优先级→复制偏移→runid)→ 通知客户端;
- 客户端通过哨兵拿当前主地址。

### 7.3 集群(Cluster,16384 个哈希槽)
- 数据分片:**CRC16(key) % 16384** 决定槽;槽分布在多个主节点;
- 每个主节点挂若干从节点(容灾);
- 客户端直连任一节点,key 不在本节点 → MOVED 重定向/ASK 迁移中重定向;
- **为什么不把 key 直接哈希到节点,而是先到槽**:节点扩缩容只移动槽,
  不用重哈希所有 key(槽是稳定的中间层);
- 多 key 操作要求同槽:用 hash tag(`{user123}.cart`)。

## 8. Redis 与 MySQL 的一致性(架构层面)

```text
读:先 Redis,miss 再 DB,回填(设置短 TTL,加锁防击穿)
写:先 DB 成功 → 删 Redis(失败补偿:重试/延迟双删/binlog 订阅删除)
```
- 最终一致性:短暂脏读可接受;
- 强一致场景(金额等):别用缓存,直接 DB + 乐观锁/行锁;
- 面试加分:聊"缓存是性能手段不是一致性手段",先想清楚读多写少才加缓存。

## 第二部分:本项目结合点

## 9. 项目现状与可引入场景

**现状**:rag_knowledge_base 未使用 Redis;会话/消息/记忆/运行记录在 MySQL,
JSONL trace 本地文件,向量在 OpenSearch。

**适合引入 Redis 的场景**(面试可主动提):
1. **会话热数据缓存**:消息列表最近 N 条缓存,打开会话秒开(降 MySQL 压力);
2. **查询扩展结果缓存**:现在 QueryExpander 是进程内存缓存(128 条上限、
   单机生效),多实例部署时 Redis 共享缓存,命中率更高;
3. **per-run 工具缓存** → 升级为"同问同答"全局缓存(带 TTL);
4. **限流**:多用户上线后按 user_id 做滑动窗口限流(INCR + EXPIRE);
5. **分布式锁**:多实例部署时索引重建/记忆整合加锁,防止并发重建;
6. **热点统计/排行榜**:RunsView 每日 token 统计、欢迎页建议轮换;
7. **审批请求(permission_request)**:现在存进程内 PermissionManager,
   多实例时不互通 → 可换 Redis(带 TTL 自动过期),顺带解决多机审批路由;
8. **任务清单/技能偏好读缓存**:todos 高频读,Redis 缓存 + 失效删除。

**引入后的一致性注意**:写 MySQL 成功 → 删缓存;todos 用"DB 为准,缓存可丢"。

## 第三部分:面试题精讲

### Q1. Redis 为什么快?单线程为什么还快?
**考察点**:IO 模型、内存、数据结构。
**答法**:① 内存操作;② 单线程 + IO 多路复用(epoll)无锁无切换;③ 数据结构
精良(跳表/SDS/哈希表);④ 协议简单。单线程的好处=无并发竞争,坏处=慢命令
阻塞全员(KEYS 改 SCAN)。
**加分**:6.0 IO 线程池(读写 socket 并行,执行仍单线程);提"Redis 瓶颈通常
是网络与内存带宽"。

### Q2. String / Hash / List / Set / ZSet 底层是什么?各用什么场景?
**答法**:SDS/哈希表+listpack、listpack→quicklist、intset→哈希表、
skiplist+dict。场景:计数、对象字段、队列、去重交并差、排行榜。
**加分**:说清"数据少用小结构(listpack/intset),量大升级"的渐进策略;
提 ZSet 排行榜的 ZREVRANGE 是范围查询,跳表为此而生。

### Q3. 缓存穿透 / 击穿 / 雪崩区别与解决?
**答法**:穿透=查不存在(空值缓存/布隆过滤器);击穿=热点 key 过期瞬间
(互斥锁/逻辑过期);雪崩=大面积过期或宕机(TTL 抖动/多级缓存/集群)。
**加分**:每种都给出"选型权衡";提布隆过滤器有误判率(可容忍才用)。

### Q4. 缓存与数据库一致性怎么保证?
**答法**:写 DB → 删缓存(更新不如删,防并发覆盖);删除失败 → 重试/延迟双删/
binlog 订阅;业务允许最终一致性。
**加分**:主动指出"读后写并发"下更新缓存会产生脏值,删除缓存则天然规避;
提强一致场景别用缓存。

### Q5. Redis 分布式锁怎么实现?有什么坑?
**答法**:SET NX EX + client_id + Lua 解锁;看门狗续期;主从切换丢锁 → Redlock
(争议)或 etcd/ZK。
**加分**:完整说坑清单:死锁(无过期)、误删别人锁(校验 value)、
超时自动释放后临界区仍在跑(看门狗)、GC 停顿(停止世界)导致锁过期。

### Q6. RDB 与 AOF 区别?为什么可以混用?
**答法**:快照 vs 追加;恢复速度 vs 丢失窗口;混合持久化= RDB 全量 + AOF 增量。
**加分**:COW fork 细节(子进程共享页表,写时复制,不阻塞主线程);
AOF 重写原理(子进程重写 + 缓冲增量,重写期间新命令双写)。

### Q7. Redis 过期删除策略?
**答法**:惰性删除(访问才删)+ 定期删除(抽样清理);为什么不用定时器
(维护成本高)。
**加分**:提"内存淘汰"与"过期删除"是两回事;过大 key 删除会阻塞
(UNLINK 异步删除)。

### Q8. 主从延迟 / 哨兵 / 集群怎么选?
**答法**:数据量 <10GB、读多写少 → 主从+哨兵(读扩展+自动故障转移);
数据量大/写并发高 → Cluster 分片。哨兵管"谁当主",Cluster 管"数据在哪"。
**加分**:16384 槽 + 哈希槽 vs 一致性哈希的对比;hash tag 同槽多键。

### Q9. 热 key / 大 key 问题?
**答法**:热 key(单个 key 被超高频访问):本地缓存分层、副本热 key
(把热 key 复制多份)、读写分离。大 key(如一个 list 百万元素):
拆 key、渐进删除(SCAN/LTRIM)、避免一次 O(N) 命令。
**加分**:提"热 key 检测"(monitor/redis-cli --hotkeys)与
"bigkeys" 扫描。

### Q10. Redis 做消息队列靠谱吗?
**答法**:简单场景 List(阻塞队列)够;可靠场景用 Stream(消费者组、
pending 列表、ACK、XCLAIM 重投)。对比 Kafka:Redis 内存型适合轻量短队列,
Kafka 适合高吞吐持久化日志。
**加分**:提 Stream 的消费者组与"未 ACK 重投"机制;提 Redis 队列丢数据
风险(内存)与 RDB/AOF 恢复的丢窗口。

### Q11. Redis 集群扩容时 key 怎么迁移?
**答法**:Cluster 按槽迁移:源节点把槽内数据增量同步(迁移中 ASK 重定向)
→ 完成后槽归属变更广播;客户端收到 MOVED 更新路由,收到 ASK 单次重试。
**加分**:讲清 MOVED(永久重定向,槽已迁移)与 ASK(临时,迁移中)的区别。

### Q12. 如何实现"附近的人"?
**答法**:GEO 结构(基于 ZSet,经纬度编码为 score)→ GEORADIUS 按圆心半径
查,GEORADIUSBYMEMBER 按成员。原理:GeoHash 空间填充曲线,邻近点 score
相邻 → ZSet 范围查询。
**加分**:讲 GeoHash 的精度分档与边界问题(相邻格子不连续,Redis 做了
邻格搜索)。

## 面试速记卡

- 为什么快:内存 + 单线程 epoll + 精良数据结构 + 简单协议;
- 数据结构:ZSet=跳表+dict;List=quicklist;Hash/Set 小数据 listpack/intset;
- 持久化:RDB 快照(fork+COW)+ AOF 追加;混合持久化兼顾速度与丢失窗口;
- 淘汰:noeviction 默认;allkeys-lru 常用;LFU 防冷门大对象;
- 三兄弟:穿透(布隆/空值)、击穿(互斥锁/逻辑过期)、雪崩(TTL 抖动/多级);
- 分布式锁:SET NX EX + client_id + Lua 解锁 + 看门狗;
- 集群:CRC16 % 16384;MOVED vs ASK;hash tag 同槽;
- 本项目:可引入场景=共享扩展缓存/限流/多实例审批/分布式锁/会话热数据。
