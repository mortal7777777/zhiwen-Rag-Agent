## 一、2026-09-11 两轮优化记录（做了什么、为什么、结果）

### 第一轮：S1 书名感知路由 + S5 相关度门槛

- **动机（问题定位）**：21 题实测发现 5 题"用户点名了书、正确书却被压"。
  根因是**书名信号不对称**：书不自称（正文说"本书"），书名高频出现在**其他书**
  的引用里 → BM25 命中的全是引用块；kNN 区分不了同主题书；**RRF 双路加成反而
  放大引用块**（引用块两路都靠前，目标书只有语义一路）。所有层都没有"实体匹配"
  通道。
- **改动**：问题里的《书名》→ 归一化匹配来源文件名（`title_matches_source`）→
  ① 融合分 ×2；② 每本保底 3 个 parent 进精排池；③ 精排分 +0.1 再截断。
- **效果**：快指标 source_recall 0.95→1.00、MRR 0.847→0.897；RAGAS precision
  0.741→0.809。API 例：点名书目的题 6/6 来源正确。
- **S5**：`/api/chat` 加 top1 门槛（`kb_chat_min_score=0.2`），低于则 0 来源
  直答"没有找到"。校准：库外题 top1 ≤0.12，库内最低 0.537；硬例"推荐科幻
  电影"0.578 拦不住（已记录，不为此过拟合）。

### 第二轮：S2 目录块治理 + S3′ 书内检索（+ S4 否决 + ac 口径修正）

- **S2 动机**：某题 6 个输出槽里 4 个是目录页（章节词密度高，BM25/reranker
  都爱给分），正文块被挤掉。
- **S2 的边界教训（本轮最贵的一课）**：强降权（×0.5/−0.15）上线后，
  **某清单类书目的答案命中从 7/7 掉到 2/7**——清单**就在这本书自己的
  目录页里**；另一题的目录条目还合法覆盖着参考答案的一部分（rec 0.5→0.0，
  重掷稳定）。**规则必须有收益面/误伤面的单题 A/B 对照**。修正：轻降权
  （×0.7/−0.08）+ **枚举题豁免**（问题含哪些/哪几/列举时不降权）。
- **S3′ 动机**：点名书的正文块在全局检索里持续被"引用块/同主题书/目录块"
  压迫。改动：store 加来源过滤（`filter_rel_path`），点名书内跑 kNN+BM25
  取 top3 保底进池。
- **S4 否决（方差受控实验）**：固定扩展结果、只变池/输出规模（pool 10/12/14
  × out 6/8），5 个顽固短语**全部无效** → 不采纳。
- **覆盖 ≠ 排序（关键认知）**：l1-kb-003 与 l1-kb-005 的目标句分别在书内
  60+ 名与第 107 名——**问题驱动的检索从原理上够不到**，任何排序/保底手段
  无效。该套题的 keyword_recall 上限 ≈0.75-0.80。此结论避免了未来在这两个
  缺口上反复浪费实验。
- **ac 口径修正**：`AnswerCorrectness` 从 `weights=[1,0]`（纯事实）改为
  `[0.5,0.5]`（+语义相似度，本地 BGE）。对照实验（同答案同上下文只换权重）
  六题均值 +0.30（l2-kb-006 +0.64、l1-kb-001 +0.40）。
- **结果**：对照 s1 基线门槛通过：rec 0.808→0.875（+0.067），faith/prec/ac
  在容差内；目录占槽 17→4。

## 二、教训清单（按"下次一定会用到"排序）

1. **实体指向必须走元数据通道**。词频/语义/排序融合都表达不了"用户点名的是
   哪本书/哪个文件"。遇到"点名实体被压"类问题，第一反应是问题文本 → 元数据
   （source/relative_path）匹配，而不是调权重。
2. **启发式规则上线前做单题 A/B**。收益面（如目录占槽减少）容易测量，误伤面
   （清单型答案、合法覆盖）必须挑"最像反例"的题去做开/关对照。S2 的教训：
   连"目录块有害"这种直觉都可能是错的——要问"对谁有害、对谁有利"。
3. **先归因、再选工具**：一个内容缺口先量"它死在那一级"（候选 40？池 10？
   输出 6？还是根本不在召回内/在书内 60 名外？）。归因结果直接决定用哪类
   修复；跳过归因会做出无效改动（S4 就是被归因实验否决的）。
4. **RAGAS 单题不可信，均值+容差可信**。三重 LLM 非确定性（查询扩展/生成/
   裁判）叠加，单题 run-to-run 可差 0.5；快指标（规则判定）也有 ±1 题波动
   （扩展查询是 LLM 生成的）。对照实验要**固定扩展结果**做方差受控比较。
5. **单题大跌先重掷甄别**：`python eval_ragas.py --id <ids>` 复用检索缓存、
   只换裁判（约 3 分钟），能区分"噪声"与"真回归"；确认是真回归再回滚/重跑。
6. **改检索必须让缓存失效**：缓存指纹 = `RETRIEVAL_VERSION` + 检索参数 +
   索引物理名 + provider。**改检索代码记得手动 `RETRIEVAL_VERSION += 1`**
   （在 `app/rag/retriever.py` 顶部）。否则评测会静默命中旧检索结果。
7. **参考答案与标注要"库内原文 + 点名书内"双验证**。反例：l1-kb-008 的
   关键词句其实只存在于姊妹书（不在点名书内），标注纠了两次。写字面/措辞类
   参考前，用 OpenSearch `match_phrase` 验证：① 措辞在库内存在；② 在
   **理论归属的那本书内**存在。
8. **judge 客户端的三个历史坑**（都已修，勿回退）：`RAGAS_DO_NOT_TRACK=true`；
   `httpx trust_env=False`（绕系统代理 Clash）；`thinking disabled` +
   显式 120s 超时 + max_retries。卡死排查顺序：单题直连 → 单样本 ragas →
   全量。
9. **ragas legacy vs collections**：`evaluate()` 只认 legacy `Metric` 类
   （`ragas/evaluation.py:133` 的 isinstance 检查）；collections（下一代 API）
   是 **async-first**，配同步客户端会报 `Cannot use agenerate()...`，诊断模式
   需 `AsyncOpenAI`（见 `eval_ragas.load_judge(use_async=True)`）；0.4.3 的
   `MetricResult.reason` 尚未填充（实测 None），`--explain` 当前价值是双实现
   交叉校验 + 1.0 迁移地基。
10. **环境坑**：本机 OpenSearch 不随开机自启（README 里的路径只是示例，以
    本机实际安装为准）；后端必须脱离沙箱启动（沙箱继承网络限制）；
    Windows 下 `run.py`（reload 模式）与 uvicorn 实例可能**同时监听 8000**
    （127.0.0.1 与 0.0.0.0 各占一个，流量被旧实例截走）——重启后 `netstat`
    确认只有一个监听者。

## 三、复用入口（命令速查）

```powershell
cd rag_knowledge_base\backend
python evaluate_retrieval.py --batch          # 内环：30 题快指标（~2 分钟，无裁判）
python eval_ragas.py --limit 3                # 快检
python eval_ragas.py                          # 全量（检索走缓存；改过检索代码会按指纹自动重跑）
python eval_ragas.py --tag 2026-09-11-s3      # 确认好基线后记录
python eval_ragas.py --explain l2-kb-011      # 裁判双实现诊断
python eval_cmrc.py --limit 120               # 公开基准（检索）
cd .. ; python scripts\regression_gate.py --skip-eval --baseline latest   # 门槛对比
```
